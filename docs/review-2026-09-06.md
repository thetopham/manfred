## Implemented: fail-closed queue confirmation

`integrations/tasker/eyevue-worker-flow.js` now independently checks the UI worker's supporting evidence before completing a receipt. A `send_confirmed` status and two attempt flags alone are insufficient. Completion also requires completed selection/send actions, observed submission/new image, validated network, enabled on-device confirmation, explicitly absent error/upload indicators, and no attempted or completed post-send focus toggle. Missing and non-boolean fields hold rather than succeeding.

Why: the Java worker snapshots images before Send, then can reveal the transcript after Send. That can expose historical images and increase the accessible Image count without proving this receipt was submitted. The queue boundary now holds this case as `confirmation_view_changed`. Incomplete positive evidence is `confirmation_evidence_incomplete`. No automatic retry, queue reset, image selection, or Send action was added.

This is conservative hardening, **not a fix for focused-Live delivery**. It can hold a genuinely sent photo after a focus toggle. It does not prove that a view stayed unchanged without a toggle or provide a server acknowledgement. The Java small-orb classifier and phone's current queue are unchanged. Reliable normalization should establish the same verified presentation before and after Send and test old-image history, an empty transcript, repeated images, and animated focused-small-orb views on the device.

The generator embeds the updated flow into the portable Tasker bundle. It takes effect only after rebuilding and carefully deploying that bundle; merging Git changes or installing an Android APK does not update installed Tasker projects. Preserve existing projects, queue and completion switch, stop the worker/dispatcher, and follow the original handoff's exact-ID/owner recovery procedure. Never retry the first already-observed image merely because it is held.

## Issues that remain open

- **#5 — Wi-Fi latency:** the first AP visit establishes the manifest baseline that excludes old originals. Removing it without equivalent file-identity evidence is unsafe. BLE counts alone do not identify files; deletions, count reuse, wraps, intervening captures and power cycles invalidate a naive cache. A reusable baseline needs device/firmware identity, freshness and invalidation rules, with a cold-start fallback and measured one-join acceptance. Persistent live streaming is a separate prototype, not proof of full-resolution still capture.
- **#6 — physical shutter:** no physical-event listener was added here. A physical press stores an original; `0x22 [31]` requests a second exposure. An opt-in preview-after-shutter implementation must disclose that distinction, require completed busy/idle plus fresh count, suppress app-originated responses, keep one capture in flight and fail closed on disconnect/cancellation. It still needs device validation.
- **#7 — Live confirmation:** partially hardened as above; small-orb normalization and actual held-queue recovery remain unresolved. No phone state was inspected or changed by this review.
- **#8 — high-resolution BLE:** the recorded complete JPEG is **320×180**, not a receiver-imposed resize. Bluetooth audio support does not demonstrate a supported full-resolution camera transfer. The matching BLE firmware package alone does not establish camera/ISP code or an unlock. Board/ISP identification, exact matching firmware, offline decoder/encoder tracing and a recovery path remain prerequisites to any proposed flash. No firmware was downloaded, executed, modified or flashed by this follow-up.

Do not close these hardware/end-to-end issues merely because PR #4 is merged. The app-button BLE preview is useful experimental functionality; reliable hands-free high-resolution Manfred glasses are not established by this review.
